# AWS / Ubuntu deployment architecture

Initial target: Internet HTTPS -> Nginx on Ubuntu EC2 -> Dockerized Spring Boot over 127.0.0.1:8080. RDS PostgreSQL and private S3 are managed external services. This session creates templates only, no resources or deployment. SQS/notification worker and possibly ECR/ECS are later evolution; no EKS/Kubernetes.

Separate local, staging and production databases, buckets, credentials, logs and image releases; preferably separate AWS accounts for staging/production. EC2 is in a public subnet for Nginx, RDS in private subnets with public access disabled. EC2 security group exposes 443; 80 only for HTTPS redirect/ACME when chosen. Administrative access prefers SSM; if SSH is needed restrict source IP, key auth and disable password/root login. RDS 5432 allows only application/migration security groups. Spring's port is loopback-only. Restrict egress where practical; no DB port open to the Internet.

Use Ubuntu LTS supported at actual deployment, patched Docker Engine/Compose and Nginx, unattended security patch policy with planned reboot checks. Nginx terminates TLS using a real hostname and automated certificate renewal; template cannot run until domain/cert paths are replaced. Only Nginx is a trusted forwarded-header source. CloudWatch-oriented structured logs and retention require an explicit setup checklist. No unreviewed remote install scripts.

Use EC2 instance role for S3 and secret retrieval; scope bucket prefixes/actions, secret ARNs and KMS keys. Block public S3, enforce TLS/encryption; RDS encryption/backups/PITR and verify-full TLS with the AWS CA bundle. Keep migration DDL identity separate from application DML identity. Never use local PostgreSQL owner credentials in prod. Runtime env file is created by operator/secret integration at /etc/dormfix/app.env, mode 0600 and outside Git. Exact IAM policy ARNs/regions are deferred until the environment exists.

Local startup runs Flyway automatically. Production profile disables auto-migration and retains Hibernate validation. The release gate must run matching Flyway validate/migrate with the migration role before switching the app image; do not rely on JPA validation to validate schema history. Use a migration artifact/tool version compatible with the application-managed Flyway and only the release's migrations. Pin and review the actual migration invocation in the CD phase; production scripts intentionally do not automate it yet.

Expand/contract migrations let old/new app revisions coexist. Before a release: verify backup/restore, validate migrations against a staging copy, estimate lock time, compare old image compatibility, record image digest and schema version. Start one release, verify readiness, then accept traffic. Single-EC2 Compose rolling replacement can have downtime; no zero-downtime claim. restart: unless-stopped plus Docker/systemd reboot enablement recovers crashes/reboots; an unhealthy health check alone does not restart a container. Use operator alerts/recovery rather than assume health implies restart.

Rollback selects a retained immutable image digest compatible with the current schema, reruns readiness and smoke tests. Never blindly reverse SQL or restore an old DB over newer writes.
